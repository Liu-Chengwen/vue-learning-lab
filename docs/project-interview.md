## 六、优先准备的三个技术问题

### 1. 如何进行 Element Plus 的业务封装？

**场景：** 任务页和组件库示例页都需要搜索、表格和编辑交互，如果每个页面分别实现，接口和行为容易不一致。

**设计：** 先确定状态由谁管理，再确定组件的 props、models、events、slots 和公开方法。

- SearchPanel 收集输入并发出查询、重置事件；页面分别保留编辑中的条件和已应用的条件。
- DataTable 根据列配置渲染，使用 `cell-{prop}` 作用域插槽定制单元格；分页、排序和选中事件交给父页面处理。
- TaskFormDialog 管理草稿、校验和关闭流程，通过异步 `submit` 函数接入保存逻辑。
- RemoteSelect 接收 `loader` 函数，内部统一管理搜索、防抖、加载、错误和重试。
- 使用 `defineExpose` 只公开需要的命令，例如清除选中、校验或重新加载；通过显式 attrs 透传保留底层扩展能力。

**讲述重点：** 表格不依赖任务 store，搜索组件不决定业务查询，特殊展示通过插槽扩展。封装提取当前场景中重复的行为，同时保留清晰的扩展入口。

**对应代码：** [业务组件目录](../src/components/business/)、[组件接口文档](component-contracts.md)、[任务页](../src/features/tasks/TasksView.vue)。

### 2. 如何避免远程搜索结果乱序？

**场景：** 用户先搜索 A，再搜索 B；A 的响应晚于 B 到达，直接赋值会把 B 的结果覆盖掉。

**处理流程：**

1. 输入侧使用尾部防抖，减少密集触发。
2. 每次执行新查询，使用 AbortController 取消上一次工作。
3. 每次请求分配递增序号；成功、失败和 finally 更新状态前检查是否仍为当前请求。
4. 只有当前请求可以结束当前 loading，旧请求的异常也不能写入当前 error。
5. 在组件作用域销毁时取消请求和防抖计时器。

**关键追问：为什么有 abort 还需要序号？** loader 可能没有实现取消，也可能在取消前已经进入后续异步处理。序号独立约束结果是否可以写入当前状态。防抖减少调用次数，请求序号控制结果归属，两者解决不同问题。

**验证方式：** 构造旧请求晚成功、旧请求晚失败以及组件卸载的场景，检查当前数据、错误和 loading。

**对应代码：** [useRequest.js](../src/composables/useRequest.js)、[useDebounce.js](../src/composables/useDebounce.js)、[RemoteSelect.vue](../src/components/business/RemoteSelect.vue)、[异步与状态测试](../tests/business-state.spec.js)。

### 3. 如何保证编辑取消不污染列表，并防止重复保存？

**场景：** 直接把列表对象绑定到编辑表单，输入时就会修改共享数据；点击取消也已经改变列表。异步校验期间快速点击保存还可能重复提交。

**处理流程：**

1. 每次打开弹窗，根据当前任务建立独立草稿；针对当前任务结构复制嵌套的 tags 数组。
2. 草稿用于表单输入，Pinia 保存已经确认的任务数据。
3. 校验前设置提交锁，整个校验和保存阶段保持锁定，阻止重复进入。
4. `await submit(draft, options)`，成功后通知父级并关闭；失败时保留草稿，允许重试。
5. 有未保存修改时确认放弃；各个关闭入口共用关闭策略，提交期间阻止关闭。
6. 卸载时取消校验和保存，await 结束后再次检查组件状态。
7. store 在模拟等待结束后再次校验，成功时一次写入；等待期间已删除的任务不能被重新创建。

**关键追问：为什么不用 `await emit('save', draft)`？** emit 用于发出通知，不能借此等待父组件监听器的异步保存结果。这里把需要等待的工作定义为返回 Promise 的 `submit` prop，保存成功的通知再使用事件。

**对应代码：** [TaskFormDialog.vue](../src/components/business/TaskFormDialog.vue)、[tasks store](../src/stores/tasks.js)、[表单测试](../tests/task-editor.spec.js)。

## 七、可以展开的另外三个亮点

### 状态按生命周期和使用范围划分

- **Pinia：** 跨页面共享的任务、学习记录和偏好。
- **页面：** 筛选、排序、页码、选中行、当前视图。
- **组件：** 表单草稿、远程选项、请求与校验状态。
- **computed：** 筛选结果、分页切片、完成比例等派生值。

例如，表格和看板从同一份任务状态派生展示；取消编辑不需要回滚 Pinia。localStorage 是持久化介质，响应式来源仍然是 Vue/Pinia。恢复时检查结构，存储失败时保留本次会话中的操作。

### 应用与 Element Plus 共享主题变量

偏好 store 将主题和主色同步到 html，应用语义变量映射到 Element Plus 的 CSS 变量，ConfigProvider 统一语言与组件尺寸。

Dialog 等弹层即使 Teleport 到 body，仍是 html 的后代，可以继承全局变量。这也提供了一个具体例子，用来解释 Vue 的逻辑组件树与 CSS 的实际 DOM 继承范围。

对应 [preferences.js](../src/stores/preferences.js)、[main.css](../src/assets/main.css)、[App.vue](../src/App.vue)。

### 实验、真实源码与复习内容关联

专题元数据关联实验入口、源码文件和问答，源码面板通过 `import.meta.glob` 配合 `?raw` 按需加载文件文本。阅读内容与运行代码来自同一份文件，减少另存示例造成的不同步。

动态加载用序号避免快速切换文件后展示旧结果。Webpack 源码收集范围只包含示例源码和配置，排除生成的 dist。源码文本分块属于教学功能的额外产物，分析体积时需要与运行模块区分。

## 八、如何回答“这个项目体现了哪些 Vue 3 与 Vue 2 的区别？”

可以选择三个亲自演示过的点，不必一次列出全部 API。

| 对比角度 | 可以结合项目讲的例子 |
| --- | --- |
| 入口和插件 | `createApp` 创建应用实例，通过 `app.use` 安装 Router、Pinia 和自定义插件；对照 Vue 2 常见的 `new Vue` 入口 |
| 逻辑组织 | Options API 与 Composition API 使用方式对照；请求、防抖等相关状态与逻辑抽为 composable，结合作用域清理 |
| 响应式 | 操作 ref/reactive、对象属性、数组和响应式 Map 的实验，解释 Proxy 与 Vue 2 常见侦测限制的差异 |
| 双向绑定 | 使用默认 `modelValue/update:modelValue` 协议、具名 model 和多个 model；`defineModel` 提供编译简写 |
| 组件边界 | Fragment 多根节点下显式确定 attrs 透传位置；通过 emits 声明事件，通过 expose 控制公开方法 |
| 内置能力 | 通过 Teleport 理解弹层位置，通过异步组件与 Suspense 实验理解加载状态；Suspense 在项目中明确标为实验性 |

Options API 在 Vue 3 中也可用；`defineModel` 等宏有具体版本要求。项目运行 Vue 3，Vue 2 主要通过参考片段进行对照，不能据此称为真实旧系统迁移经历。

## 九、其他常见追问与回答要点

| 追问 | 回答要点 |
| --- | --- |
| 为什么用 Pinia，所有状态都放进去吗？ | 共享业务状态才进入 store；页面和组件临时状态就近管理，减少耦合。computed 派生统计，action 集中更新。 |
| 筛选和分页在哪里执行？ | 目前数据量小，在前端 computed 中执行。接后端时让页面管理查询参数，将结果和 total 传给表格，表格接口可以保留。 |
| 为什么使用 hash 路由？ | 当前适合本地和静态托管，刷新详情路径方便；改 history 需要部署服务配合入口回退。 |
| 持久化数据坏了怎么办？ | 读取捕获异常、检查结构和枚举；任务数据还检查 ID 唯一性。写入失败展示提示，继续保留内存状态。 |
| Vue 3 的闭包在项目哪里体现？ | useDebounce 的 timer、useRequest 的请求序号和 controller 都由闭包保存；每次调用 composable 可形成独立状态。 |
| 有哪些性能相关实践？ | 路由和源码按需加载、搜索防抖、显式组件导入、真实构建体积报告。Element Plus 样式当前全局导入；没有做完整性能基准或量化提升统计。 |
| Vite 和 Webpack 在项目中如何使用？ | Vite 构建主应用，Webpack 构建独立 Vue 示例。实际观察动态 import、HMR、代理和构建分块，分别说明 loader 与 plugin 的职责。 |
| 开发代理上线后还能用吗？ | `server.proxy` 只在开发服务中执行，静态产物不会自带代理；接真实后端时需另外配置部署入口和 API 地址。 |
| 测试主要测什么？ | 测组件公开行为及状态边界，例如重置筛选、取消编辑、重复提交、旧请求返回和卸载清理；布局与动画另做浏览器检查。 |

## 十、建议的 3～5 分钟演示顺序

1. **学习总览：** 简单说明项目背景和模块，控制在 20 秒左右。
2. **任务工作台：** 筛选与重置、表格/看板切换、新建或编辑任务；修改后取消，再打开确认原值未变。
3. **组件库页：** 展示同一业务组件在另一场景复用，切换主题并打开弹窗，解释封装接口和主题继承。
4. **源码阅读：** 选一个你熟悉的实现，例如 useRequest 的请求序号或表单草稿，结合代码说明问题和处理过程。
5. **Vue 对照实验：** 选择多 v-model 或 key 与组件身份实验，操作后解释现象。

现场使用已经验证过的本地服务或当前有效的演示链接。临时隧道地址可能变化，简历中优先放可长期访问的部署地址或仓库地址。

## 十一、项目范围、验证与后续计划

当前任务模块采用 **Pinia + localStorage + 本地异步模拟服务**，筛选分页在前端完成。独立 Node mock 用于验证开发代理。项目以单浏览器学习和演示为范围，尚未接入账号、权限或云端同步。

主构建工具是 Vite，Webpack 是独立对照示例；Element Plus 用于实际页面，Ant Design Vue 提供参考对照。组件定制通过公开接口、组合和 CSS 变量完成。

仓库现有[验收记录](verification.md)记录了 **8 个测试文件、38 项测试通过**，以及 Vite / Webpack 构建、格式检查、Chrome 桌面和窄屏代表性检查。本次整理介绍稿没有重新执行这些测试；这些记录也不代表完整跨浏览器或性能基准验收。

面试问后续计划时，按岗位选择一至两个方向即可：

- 接入真实后端，把本地筛选分页替换为接口查询，明确接口错误和数据同步策略。
- 用 TypeScript 为组件 props、models、slots 和异步 loader 建立类型约束。
- 接入持续集成，自动运行测试、构建和格式检查，再完成固定网址部署。
- 在网络与性能面板取得基线后，评估首屏依赖和组件库样式加载，按测量结果继续优化。

下一步最有帮助的准备，是不看稿回答三个问题：**数据分别放在哪里、旧请求为什么不能写回、取消编辑为什么不修改列表。** 能沿着代码说明这三个问题，就有一条清晰的项目介绍主线。
